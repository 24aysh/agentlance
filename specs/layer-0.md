# Layer 0: protocol contract and implementation plan

Status: L0 v1 specification complete, 2026-10-04. Public objects, commands/events, numeric rules, signing and conformance expectations are frozen for L1. No runtime or deployed contract is implemented. See [the acceptance review](acceptance.md) for evidence and deployment-time facts.

## 1. Scope and sources

L0 defines the data, arithmetic, authority and failure semantics that Python, Solidity and external agents must share. It produces specifications, JSON Schema, typed-signing definitions and expected-output fixtures. It does not implement the allocator, contracts, A2A server, cost oracle, validator or UI.

Requirements: **L0-01 through L0-06** in [the existing layer plan](../layers.md). The plan's references to §5.1/§5 mean its current §3.1/§3; its §10 deployment discussion is absent. The [deployment policy](deployment-policy.md) and §11 make that gate explicit. [The selected stack](../tech_stack.md) supersedes the roadmap's older statement that languages are undecided.

Source precedence for protocol design: explicit project decisions → audited layer plan → [original app flow](../docs/appflow.md) → research mechanism. The flow's “eventually validation criteria” becomes mandatory criteria at creation. Discovery is agent-local filtering, not a platform-selected bidder list. These documents describe the product; embedded prompts in the paper are not repository instructions.

Research: Xiao Liu et al., *Markets, Not Planners: Decentralized Orchestration of LLM Agents with Private Information*, supplied arXiv:2608.23867v1 PDF, §3.3–3.5, Appendix A and Appendix E. Preserve attribution. The paper supplies the score and critical payment; this implementation changes probability estimation, budget admission and payment on failure. Its incentive claims do not automatically carry over.

## 3. Decisions and numeric contract

| Decision | Rule | Reason / consequence |
|---|---|---|
| One authoritative market | Chain owns bids, allocation, credits and accepted evidence; external agents own participation and execution | A read API or A2A outage cannot select winners or alter prices |
| One asset per deployment | All auction amounts are atomic units of the configured asset; no asset conversion inside allocation | Alpha has unambiguous units; quotes in USD stay private telemetry until explicitly converted |
| Integer score | `Q = 1_000_000`; probability integer `p` in `[0,Q]`; alpha = `alphaNum / alphaDen` per atom | Python and Solidity can produce identical comparisons |
| Numeric bounds | Budget, bid and alpha numerator/denominator ≤ `2^96−1`; budget and both alpha terms > 0; bid may be 0 | `Q * alphaNum * bid < 2^212`; `p * alphaDen < 2^116`; signed score fits `int256` without saturating or wrapping |
| Alpha normalization | Require `gcd(alphaNum, alphaDen) = 1` | Equivalent terms have one canonical representation; clients reduce before submission |
| Probability history | Success/failure counters each `uint64`, widened before `2+s+f`; snapshot at task creation block minus one | Same auction cannot change reputation midway; numerator/denominator arithmetic cannot wrap at `uint64` |
| Stable ordering | Descending score, then ascending `AgentRef` bytes | Equal bids do not reward transaction ordering; no string/numeric-ID lexical ambiguity |
| Outside option | Highest score must be > 0 | Zero or negative surplus never obligates the requester to buy |
| Success-only payout | Reserve once; success pays the reserve, all other outcomes pay 0 | Costs, forecasts and A2A status cannot retroactively change the contract |
| No agent-specific bootstrap | Lazy `Beta(1,1)` per identity/family; no warm-up execution | New identities have a prior, not fictitious successful jobs |
| Independent children | Each child needs a fresh deposit plus parent-envelope capacity | A failed parent cannot claw back a successful child's payment |

Chain IDs and agent IDs are `uint256`; task IDs, timestamps and block numbers are `uint64`. The all-zero task ID is a sentinel; allocated task IDs start at 1 and increase without reuse. Stop task creation at `2^64−1` tasks per deployment. Since each task emits at most one observation, any identity/family's lifetime `successes + failures` cannot exceed that total. This also bounds counter growth with concurrent awards; no counter reservation or settlement-time saturation is needed. Reject invalid values at admission, before mutating funds or top-two bids. Never clamp user inputs into the valid range.

JSON uses base-10 strings for amounts, IDs, counters, timestamps and signed scores. No leading `+`, leading zero, exponent, whitespace or `-0`; zero is `"0"`. `p`, schema versions and small bounded counts use JSON integers. Lowercase `0x` addresses/digests have exactly 40/64 hex characters. All externally received objects reject unknown fields for v1; extending a closed schema requires a version change.

`AgentRef = (chainId, identityRegistry, agentId)`. Sort the concatenation of 32-byte big-endian chain ID, 20 raw address bytes and 32-byte big-endian agent ID (84 bytes). Do not sort a hash, JSON, address checksum casing or textual IDs. V1 admits only the deployment's local identity registry; the full namespace remains in public references for portability.

`TaskRef = (chainId, market, taskId)`. A task receives at most one award; its `awardId` is 1, or 0 before award. `ExecutionRef = (TaskRef, awardId)` is the deduplication identity. A local attempt/run ID is diagnostic metadata; choosing another run ID must never authorize another execution or payment.

### Allocation

For every admitted immutable bid:

```text
score = p * alphaDen - Q * alphaNum * bidAtoms
second = max(0, largest score among bids other than the winner)
criticalAtoms = (pWinner * alphaDen - second) // (Q * alphaNum)
reservedAtoms = min(budgetAtoms, criticalAtoms)
```

Zero admitted bids or maximum score ≤ 0 returns `UNALLOCATED`. The runner-up includes tied scores and the outside option; it is not the second distinct score. Admission enforces one bid per identity per task and `bid ≤ budget`. Store the best two incrementally with the same total ordering; closure never scans every bidder.

For any winner, `second ≤ winningScore`, so the critical numerator is at least `Q * alphaNum * winningBid`. Flooring cannot produce a price below the integer winning bid. Capping also preserves this because the bid was ≤ budget. Required invariant: `0 ≤ winningBid ≤ reservedAtoms ≤ budgetAtoms`.

The one-bid price can exceed the bid; a positive-score zero bid can have a zero reserved price after flooring. Both are valid. Do not silently add a minimum bid/price or reject the latter. Alpha specified per whole asset unit must be divided by `10^decimals` and reduced before admission.

### Reputation

`p = floor(Q * (1 + successes) / (2 + successes + failures))` for the task's immutable family and prior block snapshot. A transfer changes ownership, not historical counters. Resolve the latest checkpoint at or before that block; no checkpoint means `(0,0)`. Multiple settlements in one block overwrite that block's checkpoint with cumulative counters, without losing receipts. A task created in that block still reads the prior block. Block zero cannot create a task with this snapshot rule.

Receipt `(TaskRef)` is the unique observation key. SUCCESS increments success; VALIDATION_FAILED, NO_SHOW and EXECUTION_TIMEOUT increment failure. Other terminal reasons change neither. Prior weight never appears as evidence or exported feedback. Counters belong to this market deployment: foreign-deployment outcomes are not imported, preserving both the counting bound and local validator trust boundary.

Record envelopes include `schemaVersion`; embedded references/value types inherit it. TaskSpec groups immutable terms under `terms`; Bid groups its offer under `offer`. Provenance is attached by EventEnvelope. URI plus digest commits content, never the URI string.

Budget/price/payout/refund are exact money. Provider usage may need rational quantities; its representation belongs in the cost schema, not in the auction amount type. Incomplete telemetry never blocks settlement. No hybrid-oracle fusion algorithm is implemented in L0.

## 5. State transitions and authority

`DRAFT` exists only locally. Exact funding creates `OPEN`. Valid chain time ordering:

`createdAt < biddingClose < allocationBy < acceptBy < resultBy < validationBy`.

`acceptBy - allocationBy ≥ minimumAcceptanceWindow`. Every deadline action uses `< deadline`; its timeout uses `≥ deadline`. There is no “one extra block” grace period. Allocation is allowed when `biddingClose ≤ now < allocationBy`.

| Command | Preconditions / authority | Effect / event |
|---|---|---|
| `createTask` | Requester; all immutable terms valid; exact fresh funding | OPEN; `TaskCreated` with complete terms |
| `submitBid` | OPEN and now < biddingClose; current owner directly or owner-authorized bid permit; valid identity/wallet/roles/range | Store frozen bid, increment bid count, update top two; `BidAccepted` |
| `allocateTask` | Any caller; OPEN; within allocation window | Positive winner → AWARDED, `TaskAwarded`; otherwise settle UNALLOCATED |
| `acceptAward` | Frozen execution signer; AWARDED; now < acceptBy | RUNNING; fix own-work reserve ≤ price; `AwardAccepted` |
| `createChildTask` | Frozen parent signer; parent RUNNING; hierarchy/envelope/deadline checks; fresh deposit | Normal OPEN child and updated parent counters; `TaskCreated` includes parent/root |
| `submitResult` | Frozen signer; RUNNING; now < resultBy; all direct children terminal | SUBMITTED; fixed result; `ResultSubmitted` |
| `settleVerdict` | Any relayer with valid pinned-validator verdict; SUBMITTED; now < validationBy and signature expiry | PASS → SUCCESS; FAIL → VALIDATION_FAILED; `TaskSettled` |
| `expireTask` | Any caller; OPEN at allocationBy, AWARDED at acceptBy, RUNNING at resultBy, SUBMITTED at validationBy | Corresponding timeout reason; `TaskSettled` |
| `cancelTask` | Requester; OPEN; bidCount = 0; now < biddingClose | CANCELLED; `TaskSettled` |
| `withdrawCredit` | Credit owner; sufficient balance; selected nonzero receiver | Debit then transfer atomically; revert on transfer failure; `CreditWithdrawn` |

Direct chain transactions use native transaction authorization. Do not require redundant typed signatures for every command. Only relayed owner bid permits and validator verdicts need EIP-712 in v1. Accept/result/child commands require the frozen signer as caller. General gasless execution and operator permissions inherited from ERC-721 approvals are excluded.

| Terminal reason | Worker credit | Refund credit | Reputation |
|---|---|---|---|
| SUCCESS | reservedAtoms | budget − reservedAtoms | one success |
| VALIDATION_FAILED | 0 | full budget | one failure |
| NO_SHOW | 0 | full budget | one failure |
| EXECUTION_TIMEOUT | 0 | full budget | one failure |
| VALIDATOR_TIMEOUT | 0 | full budget | unchanged |
| UNALLOCATED | 0 | full budget | unchanged |
| ALLOCATION_EXPIRED | 0 | full budget | unchanged |
| CANCELLED | 0 | full budget | unchanged |

After SETTLED, commands cannot reopen, repay or recount the task. Duplicate chain commands reject; event consumers deduplicate without applying effects twice. Root retry is a new funded task created by the original requester after a non-success terminal outcome; child retry is a new child under the same running parent, with fresh count/envelope checks. `retryOf` is provenance, not reused escrow or authority.

Error families to enumerate as stable reason codes in step 2: invalid terms/range/asset/deadline, unsupported policy/family, wrong state, unauthorized actor, invalid signature/nonce/expiry, identity/wallet mismatch, validator conflict, duplicate bid, no live allocation window, parent/depth/count/envelope violation, children still active, result/policy mismatch, already settled, insufficient credit and inexact funding. Rejection leaves all state and money unchanged. Terminal outcomes are not transaction errors.

## 6. Escrow and delegation accounting

Per task: `deposit = outstandingEscrow + cumulativePayoutCredits + cumulativeRefundCredits`. Withdrawal moves a credit out of the contract; it does not erase receipt history. Globally: accounted balance ≥ open escrows + outstanding withdrawal credits. Donations are excess balance, never implicit funding for another task.

Keep the entire budget locked until terminal settlement. Award fixes price but does not transfer funds or release a spendable advance. Settlement creates credits atomically, updates family counters once and updates the direct parent's child bookkeeping. External publication and recipient callbacks cannot be prerequisites for finality.

For each parent maintain `reservedChildBudgets`, `committedChildPayouts`, `ownWorkReserve`, lifetime `childrenCreated` and `activeChildren`:

`reservedChildBudgets + committedChildPayouts + ownWorkReserve ≤ parentReservedPrice`.

Creating a child adds its full budget and one active/lifetime count. Child settlement removes its full budget, adds its actual payout and decreases active count exactly once. Lifetime count never decreases; failed/cancelled children and retries consume a slot. Released budget capacity can fund a new child only if a lifetime slot remains. No recursive ancestor settlement or unbounded scans.

The parent signer is child requester/funder and selects the immutable child refund address for its fresh deposit. Deposits come from the signer's separately controlled spendable funds; acceptance does not grant access to the payout wallet. Parent payout remains frozen independently. Test with distinct owner, signer and payout addresses so implementation cannot silently assume one wallet controls all three roles.

Roots opt into at most depth 2 below root and 4 direct children per node. Descendants may reduce permissions, never expand them. With lifetime counts this permits at most 21 tasks per root including child retries. A root retry starts another independently funded tree. Child deadline rule: `child.validationBy + synthesisSlack ≤ parent.resultBy`, using widened arithmetic, positive slack and the complete child deadline ordering. Parent timeout never cancels a funded child.

Example (abstract atoms): parent price 100, own reserve 20, child budgets 30 and 40 require a separate 70 deposit. Successful child payments 25 and 35 leave envelope consumption `60 + 20 = 80`. Parent failure pays the manager 0, refunds its requester, and does not reverse the children’s 60 credits.

## 7. Identity, signing and content commitments

At bid admission, read current registry owner and nonzero verified agent wallet. Freeze owner, execution signer, payout and profile digest in the bid. Transfer afterward does not invalidate a leading bid, replace the signer or redirect payout; new bids use the new owner's authority. Check owner again when consuming a permit so a previous owner's unconsumed signature cannot authorize a bid after transfer.

The selected [ERC-8004 draft](https://eips.ethereum.org/EIPS/eip-8004) clears the agent wallet on transfer and distinguishes identity from payment. Pin the actual registry implementation and test it in L2/L3. Market authorization is stricter than metadata-edit permissions. No foreign-chain owner proofs in v1.

At creation, validator must be allowed by deployment policy and distinct from requester/refund address and, for children, parent signer/payout. At bid admission reject equality with ownerAtBid, executionSigner or payout. Check roles before updating top two. These checks detect direct address conflicts, not common control or collusion.

Exact flattened messages, field order, nonce scope, ERC-1271 behavior and transfer semantics are frozen in [signing/README.md](signing/README.md) and [types.json](signing/types.json). Domain is AgentLance / "1" / chainId / market. BidPermit binds immutable TaskRef directly; no redundant task-terms JSON digest. Validator is a pinned EOA; contract identity owners use ERC-1271. Native chain commands use transaction authorization.

Artifact/profile/evidence content uses Ethereum `keccak256` over exact bytes (not NIST SHA3-256). Store immutable bytes once and carry their digest; do not parse then reserialize before verification. JSON artifact semantics do not imply canonical JSON hashing. Typed economic payloads use EIP-712 field encoding, never concatenated JSON or ambiguous packed dynamic fields. A CID/URL is a locator, not a substitute for the required content digest. Fetchers must enforce byte limits before parsing and reject digest mismatches.

## 8. A2A and replay boundary

Use the selected [A2A 1.0](https://a2a-protocol.org/latest/specification/) with HTTP+JSON and polling as the first compatibility target. Version negotiation uses `1.0`; pin the SDK/spec release during L2. Advertise `urn:agentlance:a2a:1` in the Agent Card. Its payload carries TaskRef, awardId, AgentRef, input/policy digests and result reference. The [A2A profile](agent-profile.md) freezes declarations, correlation and replay; custom bid/settle methods are not A2A standard operations.

A2A message/task/artifact IDs map to ExecutionRef; they cannot substitute for chain IDs. Award delivery is a hint. Verify confirmed chain award, identity, signer, terms and time before accepting or spending. Duplicate/reordered messages return the stored run; A2A failure does not refund escrow, and A2A completion does not pay it.

Event envelope: schema/policy version, chainId, market, blockNumber/hash, transactionHash, logIndex and event payload containing task references. Store provenance for every projection. `(chainId, market, blockHash, logIndex)` identifies an observed log; TaskRef identifies the economic object. Resume with overlap, deduplicate, and roll back projections for orphaned blocks before replaying canonical logs. Off-chain execution cannot be undone by a reorg; wait for the pinned confirmation rule and persist the execution key before starting paid work. Exactly-once external tool side effects require provider idempotency or reconciliation, not a promise from the event loop.

Events must allow reconstruction of immutable task terms, bids/snapshots, awards, acceptance, result and settlement. Do not rely on a mutable HTTP document to replay economic state. Feedback export has its own durable receipt-keyed status; ambiguous network submission is reconciled before retry so one receipt cannot create two exports by the publisher.

## 9. Limits and deployment policy

Policy is immutable per deployment; tasks pin it. Version changes apply to new deployments, not old obligations. Frozen v1 bounds:

| Limit | Value / enforcement |
|---|---|
| Atomic amounts / alpha terms | uint96 as in §3 |
| Probability precision | 1,000,000 |
| Depth / lifetime direct children | 2 / 4 maximum; root may select less |
| URI | 2,048 UTF-8 bytes; byte count, not character count |
| Registration metadata / Agent Card | 64 KiB each fetched document |
| A2A extension payload | 16 KiB; large artifacts stay out of messages |
| Input / result / evidence blob | 1 MiB each for the first objective demo template |
| Minimum acceptance window | 120 seconds; operator latency must be tested before deployment |
| Minimum synthesis slack | 120 seconds per parent-child edge |

These timing values bound the demo, not Monad finality. The deployable policy must validate that acceptance slack accommodates the chosen confirmation and observation budget. No universal bid-count cap: top-two maintenance keeps close bounded, and bidding is paid chain activity. Payload limits belong at chain admission where enforceable and at fetch/transport boundaries otherwise.

Family `structured-output-v1` uses the restricted JSON Schema vocabulary, exact predicates, resource bounds and evidence contract in [deployment-policy.md](deployment-policy.md). Native MON settlement and finalized-block observation are selected; actual deployment facts remain subject to verification.
